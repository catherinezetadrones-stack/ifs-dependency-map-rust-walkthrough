    What the program is for

    IFS Cloud ships its source as a Core folder that you never edit. Your company's changes live in a separate Cust folder, mostly as -Cust files that layer over Core files of the same name. The tool reads both folders, builds one dependency graph across them, and reports problems that only show up once your Cust layer is applied: include cycles, duplicate definitions, a missing @Override, undeclared component connections, columns made ambiguous, datatypes that don't match, and what an IFS upgrade changed under your customizations. It never writes to either folder.

    The data model in one picture

    Everything ends up in one Index struct (model.rs, ). It owns seven vectors, and every link between them is a number or a string id, never a Rust reference:

    files: Vec<SourceFile>one per file read · root = Core or Cust · unit → "u12"
    units: Vec<Unit>logical name: X.fragment + X-Cust.fragment = one unit · files → [19, 35]
    objects: Vec<Object>a declaration: entity, command, procedure… · unit → "u12", file → 35, base → "o40"
    relations: Vec<Relation>a database table or view, by name · defs → files and lines
    edges: Vec<Edge>from/to are ids of a unit (u), object (o) or relation (r). Five kinds link units (include, uses_projection, implicit_include, implements, calls). Ten link objects (reference, array, enumeration, entityset_for, binds, overrides, calls_operation, implemented_by, invokes, reads).
    components: Vec<Component>SHPORD, MPCCOM… with deploy.ini connections
    findings: Vec<Finding>rule, severity, message · nodes → ids · edges → edge numbers · location → file + line · evidence and a suggested fix

    The arena pattern: indices instead of references
    
    
    Index owns every Vec: files, units, objects, edges. Everything else points into those vectors by number (file: usize, files: Vec<usize>) or by string id ("u12"). If Unit held &SourceFile instead, it would need a lifetime parameter (Unit<'a>), and Index would hold references into itself. That's a self-referential struct, which safe Rust doesn't allow. The other ways out are Rc<RefCell<…>> everywhere, or indices.
    
    
    Indices win here. The data is built once and then read, ids serialize straight to JSON for the UI, and a usize is Copy, so you can hold as many as you like without borrowing anything. The cost is that the compiler no longer checks that an index is valid. A wrong number panics at runtime (out of bounds) instead of failing to compile.

    A complete function in 50 lines, using about a dozen everyday Rust idioms. It walks a directory tree without recursion and returns what it found plus notes about what it skipped.

      2. 
    
    2. to_path_buf() makes an owned copy, because the stack has to own its entries. Later entries come from entry.path(), which returns new PathBufs.
      3. 
    
    3. while let Some(dir) = stack.pop() is iterative depth-first search. pop() moves the PathBuf out of the Vec into dir, and the loop ends when it returns None.
      4. 
    
    4. Matching on a Result to log the error and continue. This is the "keep going on errors" style. A ? here would abort the whole scan because one folder was unreadable.
      5. 
    
    5. read_dir yields io::Result<DirEntry> items. Result implements IntoIterator (an Ok gives one item, an Err none), so .flatten() silently drops entries that failed to read.
      6.

      7. 
    
    7. to_string_lossy() returns Cow<str> ("clone on write"). It borrows when the OS name is valid UTF-8 and allocates only when it has to replace bad bytes. into_owned() gives you a String either way.
      8. 
    
    8. Option and Result combinators instead of nested match: map transforms the success value, and unwrap_or supplies the fallback. The closure takes m by value and passes &m on.
      9.

      11.

    The .entity reader: XML without a crate
    
  
    crates/ifsdep-core/src/entity.rs · feeds generated getters (stage 3), generated view and table (stage 5), DATATYPE_MISMATCH, ENTITY_CHANGED

    Structs that refer to each otherArena: one owner (Index) with Vecs, links stored as usize or string ids
    
      
    Read one thing while building anotherKeep the data being built in a local variable and move it into the struct at the end  
    
      
    A closure blocks later changesPass the borrow as a closure parameter instead of capturing it  
    
      
    Push to a Vec you're iterating overCollect what you need into an owned Vec first
    
      
    A borrow is still alive at a writeClone the small thing, or reorder so the last use comes first (NLL) 
    
      
    A memoized result is needed by several callersStore Rc<T> in the cache and hand out clones
    
      
    A cache behind &self in recursive codeRefCell, keeping each borrow_mut() short
    
      
    Two &muts into one slicesplit_at_mut
    
      
    Move out from behind &mutOption::take, mem::take 
    
      
    Different closures in if branchesBox<dyn Fn>, then &*boxed
    
      
    A & to a fallback value lives too brieflyBind the fallback to a variable in an outer scope
    
      
    Output varies from run to runBTreeMap/BTreeSet or an explicit sort before anything is numbered 
    
      
    Work on another threadmove closure, 'static data, atomics for flags
